# 查询驱动的重置时间校准（Query-Driven Schedule Calibration）

ADR-0014 的重置时间对齐只在调度器「耗尽恢复」触发后覆写 `nextResetTime`，且明确否决了「反推调度属性」。我们决定推翻该否决项：**任何途径**（页面刷新自动查询、手动点击查询、冷却期确认重查、调度器耗尽恢复）触发的周期性订阅额度查询成功后，都用返回的 `resetTime` 反推并持久化 schedule 的周期配置字段——weekly 反推 `dayOfWeek` + `timeOfDay`，monthly 反推 `dayOfMonth` + `timeOfDay`（均在 schedule 自己的时区下取值，分钟截断）,fiveHour 无可反推属性、仅更新锚点；同时 `nextResetTime` 双写为 API 原值。调度器路径与查询路径复用同一套校准逻辑。

## Considered Options

- **反推调度属性（选定）**：即 ADR-0014 否决过的方案。当时的否决理由如今可接受：时区换算有 `extract*FromDate` 现成工具且与计算口径一致；31→28 漂移会被下次查询自愈（校准在每次查询后重新发生，而非只在耗尽恢复时）；「悄悄改写表单值」正是本需求的目标——用户明确选择以供应商查询结果为权威源。
- **仅扩展触发面、维持只覆写 `nextResetTime`**：改动最小，但 weekly/monthly 的错位会在每次属性重算后复现（0014 的「瞬态对齐」副作用），查询越频繁、配置与现实的偏差越刺眼。否决。
- **新增锚点字段**：0014 已否决，理由不变。

## Consequences

- ADR-0014 的「瞬态对齐」副作用被治愈：weekly/monthly 的配置被反推后，属性重算不再跳回错位值。
- **monthly 29/30/31 号会向月末漂移**是已知行为：clamp 后锚在月末，直到下次查询校准回来。接受，不特殊处理。
- `nextResetTime`（API 原值，秒级）与配置字段（分钟精度）之间存在 ≤59s 的固有微小差：前者管「这一次」，后者管「以后的周期模式」，职责分离。
- usage 查询路由在响应中附带校准后的完整订阅（脱敏），前端经 `onSubscriptionUpdate` 回调局部替换列表数据，卡片与表单值无需刷新即与服务端一致。
- 守卫沿用 0014 全套：bucket 缺失、时间戳非法或非未来、schedule 被禁用/删除、值无变化——均跳过或只记日志不写盘。
